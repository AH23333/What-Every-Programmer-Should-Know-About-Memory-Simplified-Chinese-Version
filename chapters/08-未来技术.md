# 第 8 章 未来的技术

在前面关于多处理器的各节中我们已经看到，当 CPU 或核心的数量继续增加时，就必须预期出现显著的性能问题。而这种规模的扩张恰恰是未来必然要面对的现实：处理器会拥有越来越多的核心，程序也必须越来越并行，才能利用 CPU 增长起来的潜力，因为单核性能不会再像过去那样快速提升。

## 8.1 原子操作的问题

对共享数据结构的访问进行同步，传统上有两种做法：

* 通过互斥，通常借助系统运行时提供的功能来实现这一点；
* 使用无锁数据结构。

无锁数据结构的问题在于，处理器必须提供能够以原子方式完成整个操作的原语。这种支持是有限的。在大多数体系结构上，支持范围仅限于原子地读取和写入一个字。实现这种原子读写有两种基本方式（参见 6.4.2 节）：

* 使用原子的比较并交换（CAS）操作；
* 使用一对加载链接/条件存储（LL/SC）指令。

很容易看出，用 LL/SC 指令就能实现 CAS 操作。正因如此，CAS 操作成为大多数原子操作和无锁数据结构的构件。

有些处理器，尤其是 x86 和 x86-64 体系结构，提供了精细得多的一整套原子操作。其中许多是针对特定用途对 CAS 操作的优化。例如，原子地把一个值加到某个内存位置上，可以用 CAS 和 LL/SC 操作实现，但 x86/x86-64 处理器对原子自增的原生支持更快。程序员有必要了解这些操作，以及在编程时让它们可用的 intrinsic 函数，不过这算不上什么新东西。

这两种体系结构的一项非同寻常的扩展是它们具备双字 CAS（DCAS）操作。这对某些应用意义重大，但并非对所有应用都如此（参见 [5]）。为了说明 DCAS 可以怎样使用，让我们试着写一个无锁的、基于数组的栈/LIFO 数据结构。使用 gcc intrinsic 的第一版尝试见图 8.1。

```c
struct elem {
  data_t d;
  struct elem *c;
};
struct elem *top;

void push(struct elem *n) {
  n->c = top;
  top = n;
}

struct elem *pop(void) {
  struct elem *res = top;
  if (res != NULL)
    top = res->c;
  return res;
}
```

*图 8.1：非线程安全的 LIFO*

这段代码显然不是线程安全的。不同线程的并发访问会修改全局变量 top，而不会考虑其他线程所做的修改。元素可能丢失，已删除的元素也可能神奇地重新出现。使用互斥是可以的，但这里我们只打算使用原子操作。

修复这个问题的第一次尝试，是在插入或删除链表元素时使用 CAS 操作。得到的代码如图 8.2 所示。

```c
#define CAS __sync_bool_compare_and_swap

struct elem {
  data_t d;
  struct elem *c;
};
struct elem *top;

void push(struct elem *n) {
  do
    n->c = top;
  while (!CAS(&top, n->c, n));
}

struct elem *pop(void) {
  struct elem *res;
  while ((res = top) != NULL)
    if (CAS(&top, res, res->c))
      break;
  return res;
}
```

*图 8.2：使用 CAS 的 LIFO*

乍看之下，这像是一个可行的方案。除非 top 与操作开始时位于 LIFO 顶部的那个元素相匹配，否则 top 绝不会被修改。但我们必须把各个层面上的并发都考虑进去。有可能另一个正在操作该数据结构的线程恰好在最糟糕的时刻被调度。这里的一种情况就是所谓的 ABA 问题。考虑一下，如果第二个线程恰好在 pop 中的 CAS 操作之前被调度，并且执行了以下操作：

1. `l = pop()`
2. `push(newelem)`
3. `push(l)`

这组操作的最终效果是，LIFO 原先的顶部元素又回到了顶部，但第二个元素已经不同了。回到第一个线程，由于顶部元素没有变化，CAS 操作会成功。但 res->c 的值并不正确。它指向的是原 LIFO 的第二个元素，而不是 newelem。结果就是新元素丢失了。

在文献 [10] 中可以找到一些建议，利用某些处理器上的一项特性来绕过这个问题。具体来说，指的是 x86 和 x86-64 处理器执行 DCAS 操作的能力。图 8.3 中代码的第三个版本就使用了这一能力。

```c
#define CAS __sync_bool_compare_and_swap

struct elem {
  data_t d;
  struct elem *c;
};
struct lifo {
  struct elem *top;
  size_t gen;
} l;

void push(struct elem *n) {
  struct lifo old, new;
  do {
    old = l;
    new.top = n->c = old.top;
    new.gen = old.gen + 1;
  } while (!CAS(&l, old, new));
}

struct elem *pop(void) {
  struct lifo old, new;
  do {
    old = l;
    if (old.top == NULL) return NULL;
    new.top = old.top->c;
    new.gen = old.gen + 1;
  } while (!CAS(&l, old, new));
  return old.top;
}
```

*图 8.3：使用双字 CAS 的 LIFO*

与其他两个例子不同，这个版本（目前）只是伪代码，因为 gcc 无法在 CAS intrinsic 中处理结构体。尽管如此，这个例子应该足以让人理解这一思路。一个代计数器被加到指向 LIFO 顶部的指针上。由于每次操作（push 或 pop）都会改变它，上面描述的 ABA 问题就不再是问题。等到第一个线程真正交换 top 指针、恢复工作的时候，代计数器已经被递增了三次。CAS 操作会失败，于是在循环的下一轮中，LIFO 正确的第一个和第二个元素会被确定下来，LIFO 不会被破坏。瞧。

这就是解决方案了吗？[10] 的作者们确实把它讲得像那么回事，而且平心而论，应该提到：可以为 LIFO 构造出允许使用上述代码的数据结构。但一般来说，这种做法和上一个一样注定失败。我们仍然有并发问题，只是换了个地方。假设某个线程执行 pop，并在检查完 old.top == NULL 之后被中断。现在第二个线程使用 pop，取得了 LIFO 原先第一个元素的所有权。它可以对这个元素做任何事，包括修改所有值，或者在元素是动态分配的情况下释放它的内存。

现在第一个线程恢复执行。old 变量里仍然填着 LIFO 先前的顶部。更具体地说，top 成员指向被第二个线程弹出的那个元素。在 new.top = old.top->c 中，第一个线程解引用了该元素里的一个指针。但这个指针所引用的元素可能已经被释放。地址空间的那一部分可能已经不可访问，进程可能崩溃。对于通用的数据类型实现来说，这是不能允许的。任何针对该问题的修补都代价高昂：内存绝不能释放，或者至少在释放之前必须确认已经没有线程再引用这块内存。考虑到无锁数据结构本应更快、并发性更好，这些额外要求完全抵消了它的任何优势。在支持这种特性的语言中，通过垃圾回收来管理内存可以解决这个问题，但这是有代价的。

对于更复杂的数据结构，情况往往更糟。上面引用的同一篇论文还描述了一个 FIFO 实现（并在后续论文中做了改进）。但这段代码有完全相同的所有问题。由于现有硬件（x86、x86-64）上的 CAS 操作[^47]只能修改内存中连续的两个字，它们在别的常见情形下根本帮不上忙。例如，在双向链表中任意位置原子地添加或删除元素就是不可能的。

问题在于，通常会涉及不止一个内存地址，而只有当这些地址的值都没有被并发修改时，整个操作才能成功。这是数据库处理中一个众所周知的概念，而解决这一困境最有希望的方案之一，恰恰就来自那里。

## 8.2 事务内存

在 1993 年那篇具有开创性的论文 [13] 中，Herlihy 和 Moss 提出用硬件为内存操作实现事务，因为仅靠软件无法高效地处理这个问题。当时，Digital Equipment Corporation 已经在与其高端硬件的可扩展性问题作斗争，那些硬件配备了几十个处理器。其原理与数据库事务相同：事务的结果要么一次性全部可见，要么事务被中止、所有值保持不变。

这里正是内存发挥作用的地方，也是上一节不厌其烦地推导使用原子操作的算法的原因。在许多场合，尤其是对于无锁数据结构，事务内存意在取代并扩展原子操作。把事务系统集成到处理器里听起来像是极其复杂的事情，但事实上，大多数处理器在某种程度上已经有了类似的东西。

某些处理器实现的 LL/SC 操作就构成一个事务。SC 指令根据该内存位置是否被动过，决定中止还是提交事务。事务内存是对这一概念的扩展。现在，参与事务的不再是一对简单的指令，而是多条指令。要理解这如何可行，值得先看看 LL/SC 指令可以怎样实现。[^48]

### 8.2.1 加载链接/条件存储的实现

如果发出 LL 指令，内存位置的值就会被载入寄存器。作为该操作的一部分，这个值会被载入 L1d。随后的 SC 指令只有在尚未被改动的情况下才能成功。处理器如何检测这一点？回顾图 3.18 中对 MESI 协议的描述，答案就很明显了。如果另一个处理器修改了该内存位置的值，第一个处理器 L1d 中该值的副本就必须被撤销。当第一个处理器执行 SC 指令时，它会发现自己必须再次把该值载入 L1d。这是处理器本来就必须能够检测到的。

还有一些细节需要解决，涉及上下文切换（同一处理器上可能的修改）以及另一个处理器写入之后缓存行被意外重新载入的情况。这些问题都可以通过策略（上下文切换时刷写缓存）和额外标志位，或者为 LL/SC 指令使用独立的缓存行来解决。总的来说，有了像 MESI 这样的缓存一致性协议实现，LL/SC 的实现几乎就是白送的。

### 8.2.2 事务内存的操作

要让事务内存普遍有用，事务就不能在第一条存储指令处结束。相反，实现应当允许一定数量的加载和存储操作；这意味着我们需要独立的提交和中止指令。稍后我们会看到，还需要一条指令，用来检查事务的当前状态以及它是否已经被中止。

需要实现三种不同的内存操作：

* 读取内存
* 读取一块稍后会被写入的内存
* 写入内存

看一下 MESI 协议就应该清楚，第二种特殊的读操作为什么有用。普通的读可以由处于 'E' 和 'S' 状态的缓存行满足。第二种读操作需要的则是处于 'E' 状态的缓存行。为什么需要第二种内存读操作，从接下来的讨论中可以窥见一二；不过更完整的描述，感兴趣的读者可以参阅关于事务内存的文献，从 [13] 开始。

此外，我们还需要事务处理，它主要由提交和中止操作组成，而我们对这些操作已经从数据库事务处理中熟悉了。不过还有一条操作，它在理论上是可选的，但要用事务内存编写健壮的程序就必不可少。这条指令让线程可以测试事务是否仍在正轨上、是否（也许）可以在稍后提交，还是事务已经失败、无论如何都会被中止。

我们将讨论这些操作实际上如何与 CPU 缓存交互，以及它们如何对应到总线操作。但在那之前，我们先看一段使用事务内存的实际代码。这有望让本节余下的内容更容易理解。

### 8.2.3 使用事务内存的示例代码

作为示例，我们重新回到贯穿全章的样例，给出一个使用事务内存原语的 LIFO 实现。

这段代码看起来与那个非线程安全的版本相当相似，这是个额外的好处，因为它让使用事务内存编写代码变得更容易。代码中新增的部分是 LTX、ST、COMMIT 和 VALIDATE 操作。这四个操作就是请求访问事务内存的方式。实际上还有一个操作 LT，这里没有用到。LT 请求非独占的读访问，LTX 请求独占的读访问，而 ST 则是向事务内存中存储。VALIDATE 操作检查事务是否仍在可提交的正轨上。如果该事务仍然正常，它返回 true。如果事务已经被标记为正在中止，它就会被真正中止，并返回一个表示这一点的值。下一条事务内存指令将启动一个新事务。因此，当事务仍在进行时，代码使用了一个新的 if 块。

```c
struct elem {
  data_t d;
  struct elem *c;
};
struct elem *top;

void push(struct elem *n) {
  while (1) {
    n->c = LTX(top);
    ST(&top, n);
    if (COMMIT())
      return;
    ... delay ...
  }
}

struct elem *pop(void) {
  while (1) {
    struct elem *res = LTX(top);
    if (VALIDATE()) {
      if (res != NULL)
        ST(&top, res->c);
      if (COMMIT())
        return res;
    }
    ... delay ...
  }
}
```

*图 8.4：使用事务内存的 LIFO*

COMMIT 操作结束事务；如果成功完成，该操作返回 true。这意味着程序的这一部分已经完成，线程可以继续前进。如果操作返回假值，通常意味着整个代码序列必须重复。这里外层的 while 循环做的就是这件事。不过这并不是绝对必要的，有些情况下放弃这项工作才是正确的做法。

关于 LT、LTX 和 ST 操作，有趣的一点是它们可能失败，却不会以任何直接的方式报告失败。程序获取这一信息的方式是通过 VALIDATE 或 COMMIT 操作。对于加载操作而言，这可能意味着实际载入寄存器的值可能是无意义的；所以在上面的例子中，必须在解引用指针之前使用 VALIDATE。在下一节中我们会看到，为什么对实现来说这是一个明智的选择。也许等事务内存真正广泛可用时，处理器会采用不同的做法。不过 [13] 的结果支持我们这里所描述的方案。

push 函数可以这样概括：事务由读取指向链表头部的指针开始。这次读请求独占所有权，因为函数稍后要写入这个变量。如果另一个线程已经启动了事务，这次加载就会失败，并把这个先天不足的事务标记为已中止；在这种情况下，实际载入的值可能是垃圾。无论其状态如何，这个值都会被存入新链表成员的 next 字段。这没有问题，因为该成员还没有被使用，而且只被一个线程访问。随后，指向链表头部的指针被赋值为指向新元素的指针。如果事务仍然正常，这次写入可以成功。这是正常情况，只有当某个线程使用所提供 push 和 pop 之外的其他代码访问这个指针时才会失败。如果在执行 ST 时事务已经被中止，那就什么都不做。最后，线程尝试提交事务。如果成功，工作就完成了；其他线程现在可以启动它们的事务。如果事务失败，就必须从头重复一遍。不过在此之前，最好插入一段延迟。如果不这样做，线程可能会陷入忙循环（浪费能源、使 CPU 过热）。

pop 函数稍微复杂一些。它同样从读取包含链表头部的变量开始，请求独占所有权。然后代码立即检查 LTX 操作是否成功。如果不成功，这一轮除了为下一轮加延迟之外不再做别的事。如果 top 指针被成功读取，说明它的状态是好的；现在我们可以解引用该指针。记住，这正是使用原子操作的代码所面临的难题；用事务内存，这种情况可以毫无问题地处理。接下来的 ST 操作只在 LIFO 非空时才执行，与原先那个非线程安全的代码一样。最后提交事务。如果成功，函数返回指向头部的旧指针；否则我们延迟并重试。这段代码中一个棘手的部分是要记住：如果事务已经失败，VALIDATE 操作会中止事务。下一条事务内存操作会启动一个新事务，因此我们必须跳过函数中剩余的代码。

延迟代码究竟如何工作，要等事务内存的硬件实现出现后才能见分晓。如果做得不好，系统性能可能会显著受损。

### 8.2.4 事务内存的总线协议

现在我们已经了解了事务内存背后的基本原理，可以深入实现的细节了。请注意，这并不是基于实际的硬件。它基于事务内存最初的设计以及对缓存一致性协议的了解。有些细节被省略了，但应该仍然可以让人洞察其性能特征。

尽管名字如此，事务内存实际上并不是作为独立的内存实现的；考虑到人们希望对线程地址空间中任意位置做事务，那样做毫无意义。相反，它是作为一级缓存处理的一部分实现的。理论上，实现可以放在普通的 L1d 中进行，但正如 [13] 指出的，这不是个好主意。我们更可能看到事务缓存与 L1d 并行实现。所有访问都会像使用 L1d 那样使用更高层级的缓存。事务缓存很可能比 L1d 小得多。如果它是全相联的，其大小就取决于一个事务能包含多少个操作。实现很可能会对体系结构和/或具体的处理器版本设定上限。可以很容易想象一个只有 16 个条目甚至更少的事务缓存。在上面的例子中，我们只需要一个内存位置；事务工作集更大的算法会变得非常复杂。未来可能会看到在任一时刻支持不止一个活动事务的处理器。缓存中的条目数会随之成倍增加，但仍然小到足以做成全相联。

事务缓存与 L1d 是互斥的。这意味着一个缓存行至多存在于其中一个缓存中，绝不会同时存在于两者之中。事务缓存中的每个槽位在任一时刻处于四种 MESI 协议状态之一。除此之外，槽位还有一个事务状态。这些状态如下（名称取自 [13]）：

**EMPTY**：该缓存槽不含数据。MESI 状态总是 'I'。

**NORMAL**：该缓存槽包含已提交的数据。这些数据同样可以存在于 L1d 中。MESI 状态可以是 'M'、'E' 和 'S'。允许 'M' 状态这一事实意味着事务提交并*不*强制把数据写入主存（除非该内存区域被声明为不可缓存或写通）。这对提升性能大有帮助。

**XABORT**：该缓存槽包含在中止时要丢弃的数据。这显然与 XCOMMIT 相反。事务期间创建的所有数据都保存在事务缓存中，在提交之前不会向主存写入任何内容。这限制了事务的最大规模，但它意味着除了事务缓存之外，其他任何内存都不必为单个内存位置去感知 XCOMMIT/XABORT 的二重性。可能的 MESI 状态是 'M'、'E' 和 'S'。

**XCOMMIT**：该缓存槽包含在提交时要丢弃的数据。这是处理器可以实现的一种优化。如果某个内存位置通过事务操作被修改，旧内容不能就这么丢掉：如果事务失败，旧内容需要恢复。MESI 状态与 XABORT 相同。与 XABORT 的一点不同是，如果事务缓存满了，任何处于 'M' 状态的 XCOMMIT 条目都可以写回内存，然后不论处于什么状态都可以被丢弃。

当启动一个 LT 操作时，处理器在缓存中分配两个槽位。牺牲槽位的挑选方式是：首先寻找该操作地址对应的 NORMAL 槽位，也就是缓存命中。如果找到这样的条目，就再定位一个槽位，复制该值，把一个条目标记为 XABORT，另一个标记为 XCOMMIT。

如果该地址尚未被缓存，则寻找 EMPTY 缓存槽位。如果一个也找不到，就寻找 NORMAL 槽位。此时如果 MESI 状态是 'M'，旧内容必须刷写到内存。如果也没有可用的 NORMAL 槽位，还可以牺牲 XCOMMIT 条目。不过这很可能是实现相关的细节。事务的最大规模由事务缓存的大小决定；而且由于事务中每个操作所需的槽位数是固定的，事务数量会在不得不驱逐 XCOMMIT 条目之前就达到上限。

如果地址在事务缓存中找不到，就在总线上发出 T-READ 请求。这就像普通的 READ 总线请求，但它表明这个请求是给事务缓存的。与普通 READ 请求一样，所有其他处理器中的缓存先获得响应的机会。如果都没有响应，则从主存读取该值。MESI 协议决定新缓存行的状态是 'E' 还是 'S'。T-READ 与 READ 的差别，在该缓存行当前正被另一个处理器或核心上的活动事务使用时体现出来。在这种情况下，T-READ 操作直接失败，不传输任何数据。产生该 T-READ 总线请求的事务被标记为失败，操作中使用的值（通常是一次简单的寄存器加载）是未定义的。回顾前面的例子可以看到，如果事务内存操作被正确使用，这种行为不会引起问题。在事务中载入的值被使用之前，必须用 VALIDATE 验证。这在几乎所有情况下都不是额外负担。正如我们在用原子操作实现 FIFO 的尝试中所看到的，我们加入的这项检查正是让无锁代码得以工作的那个缺失的特性。

LTX 操作与 LT 几乎相同。唯一的区别是总线操作是 T-RFO 而不是 T-READ。T-RFO 与普通的 RFO 总线消息一样，请求缓存行的独占所有权。得到的缓存行状态是 'E'。与 T-READ 总线请求一样，T-RFO 也可能失败，此时使用的值同样是未定义的。如果缓存行已经在本地事务缓存中并处于 'M' 或 'E' 状态，那就什么都不必做。如果本地事务缓存中的状态是 'S'，则必须发出总线请求，使所有其他副本失效。

ST 操作与 LTX 类似。值首先在本地事务缓存中被独占地准备好。然后 ST 操作把该值复制到缓存中的第二个槽位，并把该条目标记为 XCOMMIT。最后，另一个槽位被标记为 XABORT，新值被写入其中。如果事务已经被中止，或者因为隐式的 LTX 失败而新近被中止，那就什么都不写。

VALIDATE 和 COMMIT 操作本身既不自动也不隐式地产生总线操作。这是事务内存相对于原子操作的巨大优势。使用原子操作时，并发是靠把改变后的值写回主存来实现的。如果你已经一路读到这里，就应该知道这有多昂贵。使用事务内存时，并不强制访问主存。如果缓存中没有 EMPTY 槽位，就必须驱逐当前的内容；对于处于 'M' 状态的槽位，内容必须写入主存。这与常规缓存没有区别，而且写回可以在没有特殊原子性保证的情况下进行。如果缓存容量足够，内容可以长时间存活。如果事务反复在同一个内存位置上执行，速度提升可能极其巨大，因为在一种情况下我们每一轮都要访问一两次主存，而使用事务内存时所有访问都命中事务缓存，它的速度和 L1d 一样快。

在事务中止时，VALIDATE 和 COMMIT 操作所做的一切，就是把标记为 XABORT 的缓存槽标记为空，并把 XCOMMIT 槽标记为 NORMAL。同样，当 COMMIT 成功结束一个事务时，XCOMMIT 槽被标记为空，XABORT 槽被标记为 NORMAL。这些都是在事务缓存上非常快的操作。不会向其他想要执行事务的处理器发出显式通知；那些处理器只能不断重试。高效地做到这一点则是另一回事。在上面的示例代码中，我们只是在合适的位置简单地写了 ...delay...。也许我们会看到处理器对延迟提供真正有用的支持。

总结一下，事务内存操作只在启动新事务时、以及把一个尚未在事务缓存中的新缓存行加入一个仍然成功的事务时，才会产生总线操作。被中止事务中的操作不会产生总线操作。不会因为多个线程试图使用同一块内存而出现缓存行乒乓。

### 8.2.5 其他考虑

在 6.4.2 节中，我们已经讨论了 x86 和 x86-64 上可用的 lock 前缀如何能在某些情况下避免编写原子操作。不过，当有多个线程在使用但并不争夺同一块内存时，所提出的技巧就不够用了。在这种情况下，原子操作是被不必要地使用的。有了事务内存，这个问题就消失了。昂贵的 RFO 总线消息只在内存于不同 CPU 上被并发使用或接连使用时才会发出；而只有在这时它们才是必需的。几乎不可能做得比这更好了。

细心的读者可能会对延迟感到疑惑。预期的最坏情况是什么？如果持有活动事务的线程被调度出去，或者它收到信号并可能被终止，或者决定用 siglongjmp 跳到外层作用域，会怎样？答案是：事务会被中止。只要线程进行系统调用或收到信号（即发生环级别切换），就可以中止事务。也有可能中止事务是操作系统在执行系统调用或处理信号时的职责之一。我们只能等实现出现之后，才能看到实际是怎么做的。

关于事务内存，这里要讨论的最后一个方面，是人们今天可能就想考虑的问题。事务缓存和其他缓存一样，以缓存行为单位操作。由于事务缓存是互斥缓存，让同一个缓存行既用于事务操作又用于非事务操作会成为问题。因此重要的是：

* 把非事务数据移出该缓存行
* 让不同事务中使用的数据位于不同的缓存行

第一点并不新鲜，今天为原子操作付出同样的努力也会有回报。第二点更麻烦，因为如今对象由于相关的高昂代价几乎从不按缓存行对齐。如果所使用的数据，连同用原子操作修改的那些字，位于同一个缓存行上，就可以少用一个缓存行。这不适用于互斥（互斥锁对象应当始终拥有自己的缓存行），但确实可以构造出原子操作与其他数据共处的情形。使用事务内存时，把一个缓存行用于两种目的很可能是致命的。对该缓存行[^49]的任何普通访问都会把该缓存行从事务缓存中移除，从而在此过程中中止事务。将来，数据对象的缓存行对齐将不仅关乎性能，还关乎正确性。

事务内存的实现可能会采用更精细的记账方式，从而不会因对属于某个事务的缓存行上的数据进行普通访问而受影响。不过，这需要付出多得多的努力，因为那时 MESI 协议的信息已经不够用了。

## 8.3 不断增长的延迟

关于内存技术的未来发展，几乎可以肯定的一点是：延迟会继续攀升。我们在 2.2.4 节已经讨论过，即将到来的 DDR3 内存技术将比当前的 DDR2 技术具有更高的延迟。FB-DRAM 如果真的部署，也可能具有更高的延迟，尤其是当 FB-DRAM 模块以菊花链方式连接时。请求和结果的传递并不是没有代价的。

延迟的第二个来源是 NUMA 的日益广泛使用。AMD 的 Opteron 在配备多个处理器时就是 NUMA 机器。CPU 旁边连着一些带有自己内存控制器的本地内存，但在 SMP 主板上，其余内存必须通过 Hypertransport 总线访问。Intel 的 CSI 技术将使用几乎相同的技术。由于每个处理器的带宽限制，以及需要服务（例如）多块 10Gb/s 以太网卡，即使每个插槽的核心数增加，多插槽主板也不会消失。

延迟的第三个来源是协处理器。我们本以为，在 1990 年代初商用处理器不再需要数学协处理器之后，就已经摆脱了它们，但它们正在卷土重来。Intel 的 Geneseo 和 AMD 的 Torrenza 是对平台的扩展，允许第三方硬件开发商把他们的产品集成到主板中。也就是说，协处理器不必再坐在 PCIe 卡上，而是被安置得离 CPU 近得多。这给它们带来了更大的带宽。

IBM 则走了一条不同的路（尽管 Intel 和 AMD 那样的扩展仍然可行），推出了 Cell CPU。Cell CPU 除了 PowerPC 核心之外，还包含 8 个协同处理单元（Synergistic Processing Unit，SPU），它们是主要面向浮点计算的专用处理器。

协处理器和 SPU 的共同点是，它们的内存逻辑很可能比真正的处理器还要慢。部分原因在于必要的简化：所有缓存处理、预取等工作都很复杂，尤其是当还需要缓存一致性时。高性能程序将越来越依赖协处理器，因为性能差距可能是巨大的。Cell CPU 的理论峰值性能是 210 GFLOPS，而高端 CPU 是 50–60 GFLOPS。如今使用的图形处理单元（GPU，即显卡上的处理器）能达到更高的数字（超过 500 GFLOPS），而且它们很可能无需太大力气就能被集成到 Geneseo/Torrenza 系统中。

由于所有这些发展，程序员必须得出结论：预取将变得越来越重要。对协处理器来说，它将是绝对关键的。对 CPU 来说，尤其是在核心越来越多时，必须让 FSB 始终保持忙碌，而不是把请求成批地堆起来。这需要通过高效使用预取指令，尽可能多地把未来的流量情况告知 CPU。

## 8.4 向量操作

当今主流处理器中的多媒体扩展只以有限的方式实现向量操作。向量指令的特点是，一条指令会产生大量的操作（单指令多数据，SIMD）。与标量操作相比，多媒体指令已经可以算是在做向量操作了，但与 Cray-1 那样的向量计算机、或 IBM 3090 这类机器的向量部件所做的事情相比，还差得很远。

为了弥补一条指令所执行操作数量的有限（在大多数机器上是四个 float 或两个 double 操作），外围的循环必须执行更多次。A.1 节的例子清楚地表明了这一点：每个缓存行需要 SM 次迭代。

有了更宽的向量寄存器和向量操作，循环迭代次数可以减少。这带来的不只是指令解码等方面的改进；这里我们更关心的是内存方面的影响。用一条指令加载或存储更多数据，处理器就能更好地把握应用程序的内存使用情况，而不必费心从单条指令的行为中去拼凑信息。此外，提供不影响缓存的加载或存储指令也会变得更有用。在 x86 CPU 中，用 16 字节宽的加载来填充一个 SSE 寄存器时，使用非缓存加载是个坏主意，因为之后对同一缓存行的访问（在缓存未命中的情况下）还得再次从内存加载数据。反过来说，如果向量寄存器足够宽，能容纳一个或多个缓存行，那么非缓存的加载或存储就不会有负面影响。对不适合放进缓存的数据集执行操作会变得更实际。

拥有大的向量寄存器并不一定意味着指令的延迟增加；向量指令不必等到所有数据都读取或存储完毕。如果向量单元能够识别代码流程，它可以从已经读取的数据开始工作。也就是说，例如要把一个向量寄存器载入，然后把所有向量元素乘以一个标量，CPU 可以在向量的第一部分载入之后就开始乘法操作。这只是一个向量单元精细程度的问题。这说明，理论上向量寄存器可以做得非常宽，而且程序今天就可以据此设计。在实践中，向量寄存器的大小受到处理器被用于多进程、多线程操作系统这一事实的限制。因此，包含寄存器值保存和恢复的上下文切换时间很重要。

有了更宽的向量寄存器，就会带来一个问题：操作的输入和输出数据可能无法在内存中顺序排列。这可能是因为矩阵是稀疏的、矩阵按列而不是按行访问，以及许多其他因素。针对这种情况，向量单元提供了以非顺序模式访问内存的方式。一条向量加载或存储指令可以被参数化，并被指示从地址空间中许多不同的位置加载数据。使用今天的多媒体指令，这完全不可能。只能把各个值逐个显式加载，然后费劲地组合到一个向量寄存器中。

过去的向量单元有不同的模式，以支持最有用的访问模式：

* 使用跨步（striding），程序可以指定相邻两个向量元素之间的间隔有多大。所有元素之间的间隔必须相同，但举例来说，这可以轻易地让人用一条指令把矩阵的一列读入一个向量寄存器，而不是每一行用一条指令。
* 使用间接寻址（indirection），可以构造出任意的访问模式。加载或存储指令接收一个指针，指向一个数组，该数组包含需要加载的真实内存位置的地址或偏移量。

目前尚不清楚主流处理器的未来版本中是否会出现真正向量操作的复兴。也许这项工作会被下放给协处理器。无论如何，如果我们能够使用向量操作，那么正确地组织执行这类操作的代码就更加重要。代码应当是自包含、可替换的，接口应当足够通用，以便高效地运用向量操作。例如，接口应当允许对整个矩阵相加，而不是对行、列乃至元素组进行操作。构件越大，使用向量操作的机会就越好。

在 [11] 中，作者们热情洋溢地呼吁复兴向量操作。他们指出了许多优点，并试图破除各种神话。不过，他们描绘的画面过于简单化了。如上所述，庞大的寄存器组意味着高昂的上下文切换时间，而这在通用操作系统中必须尽量避免。看看 IA-64 处理器在上下文切换频繁的操作上遇到的问题就知道了。如果涉及中断，向量操作的执行时间长也是个问题。如果产生中断，处理器必须停下当前的工作，开始处理中断。之后，它必须恢复执行被中断的代码。在一条指令执行到一半时中断它通常是个大问题；这并非不可能，但很复杂。对于运行时间很长的指令，要么必须这样做，要么指令必须以可重启的方式实现，否则中断响应时间就太长。后者是不可接受的。

向量单元在内存访问的对齐方面也曾很宽容，这塑造了当时所开发的算法。今天的一些处理器（尤其是 RISC 处理器）要求严格对齐，因此向完整向量操作的扩展并非易事。拥有向量操作有巨大的潜在好处，尤其是当支持跨步和间接寻址时，因此我们可以期望在未来看到这一功能。
