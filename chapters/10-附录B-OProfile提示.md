# 附录 B 一些 OProfile 提示

一些 OProfile 提示

以下内容并不是一份关于如何使用 oprofile 的教程。关于这个主题已经有整本的文档。它只是想就如何看待自己的程序以找出可能的故障点，给出若干较高层次的提示。但在那之前，我们至少需要有一个最基本的介绍。

## B.1 OProfile 基础

Oprofile 分两个阶段工作：先是收集，然后是分析。收集由内核完成；它无法在用户层完成，因为这些测量要使用 CPU 的性能计数器。这些计数器需要访问 MSR，而这又需要特权。

每一款现代处理器都提供自己的一组性能计数器。在某些体系结构上，其中一部分计数器由所有处理器实现共同提供，而其余的则随版本不同而有差异。这使得给出关于 oprofile 使用的通用建议变得困难。目前还没有（尚没有）更高层的计数器抽象能够隐藏这些细节。

处理器版本还决定了在任意时刻可以跟踪多少个事件，以及以何种组合跟踪。这又给整个画面增添了更多复杂性。

如果用户了解性能计数器的必要细节，就可以用 `opcontrol` 程序来选择应当计数的事件。对于每个事件，都必须指定“溢出数”（overrun number，即在 CPU 被中断以记录一个事件之前必须发生的事件数）、该事件是否应在用户层和/或内核中计数，以及最后还有一个“单元掩码”（unit mask，它选择性能计数器的子功能）。

要在 x86 和 x86-64 处理器上对 CPU 周期计数，必须发出以下命令：

```bash
opcontrol --event CPU_CLK_UNHALTED:30000:0:1:1
```

数字 30000 就是溢出数。选择一个合理的值，对系统的行为和所收集的数据都很重要。要求获得事件每一次发生的数据是个坏主意。对许多事件来说，这会让机器陷入停顿，因为它全部的工作都只是处理该事件溢出所触发的数据收集；这就是 oprofile 强制规定最小值的原因。每个事件的最小值各不相同，因为不同的事件在正常代码中被触发的概率不同。

选择一个非常大的数字会降低性能分析的分辨率。每次溢出时，oprofile 记录当时正在执行的指令的地址；对 x86 和 PowerPC，在某些情况下它还可以记录回溯（backtrace）。⁵¹ 分辨率粗糙时，热点可能得不到有代表性的命中数；这一切都与概率有关，这正是 oprofile 被称为概率型性能分析器的原因。溢出数越低，对系统的减速影响越大，但分辨率越高。

如果要分析某个特定的程序，而系统又不是用于生产环境，那么通常最有用的是使用尽可能低的溢出值。每个事件的确切值可以用以下命令查询：

```bash
opcontrol --list-events
```

如果被分析的程序会与另一个进程交互，而减速又给这种交互带来问题，那么这可能会有麻烦。如果某个进程有实时性要求，而在它被频繁中断时无法满足这些要求，也可能出问题。在这种情况下必须找到折中方案。如果要在一段较长的时间内分析整个系统，情况也是如此。低溢出数意味着严重的减速。无论如何，oprofile 和任何其他性能分析机制一样，都会引入不确定性和不准确性。

性能分析必须用 `opcontrol --start` 启动，可以用 `opcontrol --stop` 停止。oprofile 活动期间会收集数据；这些数据先在内核中收集，然后分批发送给一个用户层守护进程，在那里被解码并写入文件系统。用 `opcontrol --dump` 可以请求把内核中缓冲的所有信息释放到用户层。

收集到的数据可能包含来自不同性能计数器的事件。除非用户在两次独立的 oprofile 运行之间选择清除已存储的数据，否则这些数字都并行保留。可以在不同场合累积同一事件的数据。如果同一事件在不同的分析运行中都出现过，则只要用户这样选择，数字就会相加。

数据收集过程的用户层部分会对数据进行解复用。每个文件的数据都单独存储。甚至还可以区分各个可执行文件所使用的 DSO，乃至各个线程的数据。这样产生的数据可以用 `oparchive` 归档。该命令生成的文件可以传输到另一台机器，并在那里进行分析。

用 `opreport` 程序可以根据性能分析结果生成报告。使用 `opannotate` 可以看到各种事件发生在哪里：是哪条指令，以及（如果有相应数据）在哪个源代码行。这使得找出热点变得容易。对 CPU 周期计数会指出大部分时间花在哪里（这包括缓存未命中），而对退休指令计数则可以找出大部分已执行指令所在的位置——两者之间有很大差别。

某个地址上的单次命中通常没有意义。统计式性能分析的一个副作用是，只执行过少数几次、甚至只执行过一次的指令也可能被记上一次命中。在这种情况下，必须通过重复运行来验证结果。

<small>⁵¹ 希望有朝一日所有体系结构都能支持回溯。</small>

## B.2 输出是什么样子

一次 oprofile 会话可以像这样简单：

```bash
$ opcontrol -i cachebench
$ opcontrol -e INST_RETIRED:6000:0:0:1 --start
$ ./cachebench ...
$ opcontrol -h
```

请注意，这些命令（包括实际的程序）都是以 root 身份运行的。这里以 root 身份运行程序只是为了简单起见；该程序可以由任何用户执行，oprofile 都能捕获到它。下一步是分析数据。用 `opreport` 我们可以看到：

```text
CPU: Core 2, speed 1596 MHz (estimated)
Counted INST_RETIRED.ANY_P events (number of instructions retired) with a unit mask of
0x00 (No unit mask) count 6000
INST_RETIRED:6000|
  samples|      %|
------------------
  116452 100.000 cachebench
```

这意味着我们收集了一堆事件；现在可以用 `opannotate` 更详细地查看数据。我们可以看到程序中记录事件最多的地方。`opannotate --source` 输出的一部分如下所示：

```text
              :static void
              :inc (struct l *l, unsigned n)
              :{
              :  while (n-- > 0) /* inc total: 13980 11.7926 */
              :    {
     5  0.0042 :      ++l->pad[0].l;
 13974 11.7875 :      l = l->n;
     1 8.4e-04 :      asm volatile ("" :: "r" (l));
              :    }
              :}
```

这就是测试的内层函数，大部分时间都花在这里。我们看到采样分散在循环的所有三行上。主要原因是，就所记录的指令指针而言，采样并不总是 100% 准确。CPU 会乱序执行指令；要重建精确的执行序列以得到一个正确的指令指针是很困难的。最新的 CPU 版本试图为少数几个选定的事件做到这一点，但一般来说这不值得花费精力——或者根本不可能。在大多数情况下这并不真的要紧。即使采样集呈正态分布，程序员也应该能够判断出发生了什么。

## B.3 开始分析

在开始分析一段代码时，人们当然可以先看程序中花时间最多的地方。那部分代码当然应该尽可能优化好。但接下来呢？程序在哪些地方花了**不必要**的时间？这个问题不那么容易回答。

这种情形下的一个问题是，绝对值并不能说明真实情况。程序中的一个循环可能占用了大部分时间，这没问题。不过，CPU 利用率高可能有很多原因。但更常见的是，CPU 使用率比较均匀地分布在整个程序中。这时，绝对值指向许多地方，因而没有用处。

在很多情况下，查看两个事件的比值是有帮助的。例如，如果没有任何衡量函数执行频率的指标，那么一个函数中分支预测失败的次数可能没有意义。是的，绝对值与程序的性能有关。每次调用的预测失败率对函数的代码质量更有意义。Intel 针对 x86 和 x86-64 的优化手册 [15] 描述了应当考察的比值（在所引文档中针对 Core 2 事件的附录 B.7）。与内存处理相关的几个比值如下。

| 名称 | 比值 | 说明 |
| --- | --- | --- |
| 指令取指停顿 | `CYCLES_L1I_MEM_STALLED` / `CPU_CLK_UNHALTED.CORE` | 指令解码器因缓存或 ITLB 未命中而等待新数据的周期比例。 |
| ITLB 未命中率 | `ITLB_MISS_RETIRED` / `INST_RETIRED.ANY` | 每条指令的 ITLB 未命中数。如果该比值高，说明代码分散在过多页面上。 |
| L1I 未命中率 | `L1I_MISSES` / `INST_RETIRED.ANY` | 每条指令的 L1i 未命中数。执行流不可预测，或者代码尺寸过大。在前一种情况下，避免间接跳转可能有帮助。在后一种情况下，块重排或避免内联可能有帮助。 |
| L2 指令未命中率 | `L2_IFETCH.SELF.I_STATE` / `INST_RETIRED.ANY` | 每条指令的程序代码 L2 未命中数。任何大于零的值都表明存在代码局部性问题，它甚至比 L1i 未命中更糟。 |
| 加载率 | `L1D_CACHE_LD.MESI` / `CPU_CLK_UNHALTED.CORE` | 每周期的读操作数。一个 Core 2 核心每周期可以服务一次加载操作。比值高意味着执行受内存读取限制。 |
| 存储顺序阻塞 | `STORE_BLOCK.ORDER` / `CPU_CLK_UNHALTED.CORE` | 因先前未命中缓存的存储而被阻塞的存储比例。 |
| L1d 阻塞加载率 | `LOAD_BLOCK.L1D` / `CPU_CLK_UNHALTED.CORE` | 因资源不足而被阻塞的 L1d 加载。通常这意味着并发的 L1d 访问过多。 |
| L1D 未命中率 | `L1D_REPL` / `INST_RETIRED.ANY` | 每条指令的 L1d 未命中数。高比率意味着预取无效，L2 被过于频繁地使用。 |
| L2 数据未命中率 | `L2_LINES_IN.SELF.ANY` / `INST_RETIRED.ANY` | 每条指令的数据 L2 未命中数。如果该值显著大于零，则硬件和软件预取都无效。处理器需要更多（或更早的）软件预取帮助。 |
| L2 需求未命中率 | `L2_LINES_IN.SELF.DEMAND` / `INST_RETIRED.ANY` | 每条指令的、硬件预取器根本没被用上的数据的 L2 未命中数。这意味着预取甚至还没有开始。 |
| 有效 NTA 预取率 | `SSE_PRE_MISS.NTA` / `SSS_PRE_EXEC.NTA` | 有效非临时预取相对于所有非临时预取总数的比例。值低意味着许多值已经在缓存中。这个比值也可以对其他预取类型计算。 |
| 迟到的 NTA 预取率 | `LOAD_HIT_PRE` / `SSS_PRE_EXEC.NTA` | 对正在进行预取的数据的加载请求相对于所有非临时预取总数的比例。值高意味着软件预取指令发出得太晚。这个比值也可以对其他预取类型计算。 |

对于所有这些比值，运行程序时都应指示 oprofile 同时测量两个事件。这保证两个计数是可比的。在相除之前，必须确保把可能不同的溢出值考虑进去。最简单的方法是把每个事件的计数器乘以它的溢出值。

这些比值对完整程序、对可执行文件/DSO 层次、甚至对函数层次都有意义。对程序看得越深入，值中包含的误差就越多。

要让这些比值有意义，还需要基准值。这并不像看起来那么容易。不同类型的代码有不同的特性，在一个程序中很差的比值在另一个程序中可能是正常的。
