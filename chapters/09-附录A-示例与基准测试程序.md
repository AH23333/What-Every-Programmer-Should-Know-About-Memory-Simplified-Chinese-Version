# 附录 A 示例与基准测试程序

## A.1 矩阵乘法

这是在 6.2.1 节的矩阵乘法的完整基准测试程序。有关使用的 intrinsic 函数的细节，请读者参阅 [Intel 的参考手册](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html)。

```c
#include <stdlib.h>
#include <stdio.h>
#include <emmintrin.h>
#define N 1000
double res[N][N] __attribute__ ((aligned (64)));
double mul1[N][N] __attribute__ ((aligned (64)));
double mul2[N][N] __attribute__ ((aligned (64)));
#define SM (CLS / sizeof (double))

int
main (void)
{
  // ... Initialize mul1 and mul2
  int i, i2, j, j2, k, k2;
  double *restrict rres;
  double *restrict rmul1;
  double *restrict rmul2;
  for (i = 0; i < N; i += SM)
    for (j = 0; j < N; j += SM)
      for (k = 0; k < N; k += SM)
        for (i2 = 0, rres = &res[i][j], rmul1 = &mul1[i][k]; i2 < SM;
             ++i2, rres += N, rmul1 += N)
          {
            _mm_prefetch (&rmul1[8], _MM_HINT_NTA);
            for (k2 = 0, rmul2 = &mul2[k][j]; k2 < SM; ++k2, rmul2 += N)
              {
                __m128d m1d = _mm_load_sd (&rmul1[k2]);
                m1d = _mm_unpacklo_pd (m1d, m1d);
                for (j2 = 0; j2 < SM; j2 += 2)
                  {
                    __m128d m2 = _mm_load_pd (&rmul2[j2]);
                    __m128d r2 = _mm_load_pd (&rres[j2]);
                    _mm_store_pd (&rres[j2],
                                  _mm_add_pd (_mm_mul_pd (m2, m1d), r2));
                  }
              }
          }
  // ... use res matrix
  return 0;
}
```

循环的结构跟 6.2.1 节的最终形态几乎完全相同。唯一的大改变是 `rmul1[k2]` 值的加载被拉出内部循环了，因为我们必须建立一个拥有两个相同元素值的向量。这即是 `_mm_unpacklo_pd()` intrinsic 函数所为。

其余唯一值得注意的事情是，我们明确地对齐了三个数组，以令我们预期会位在同个缓存行的值真的在那里找到。

## A.2 调试分支预测

如果按第 6.2.2 节所建议的那样使用 likely 与 unlikely 的定义，那么很容易得到一个调试模式[^50]，用来检验这些假设是否真的成立。这两个宏的定义可以替换为下面的内容：

```c
#ifndef DEBUGPRED

# define unlikely(expr) __builtin_expect (!!(expr), 0)

# define likely(expr) __builtin_expect (!!(expr), 1)
#else
asm (".section predict_data, \"aw\"; .previous\n"
     ".section predict_line, \"a\"; .previous\n"
     ".section predict_file, \"a\"; .previous");

# ifdef __x86_64__

#  define debugpred__(e, E) \
  ({ long int _e = !!(e); \
     asm volatile (".pushsection predict_data\n" \
                   "..predictcnt%=: .quad 0; .quad 0\n" \
                   ".section predict_line; .quad %c1\n" \
                   ".section predict_file; .quad %c2; .popsection\n" \
                   "addq $1,..predictcnt%=(,%0,8)" \
                   : : "r" (_e == E), "i" (__LINE__), "i" (__FILE__)); \
     __builtin_expect (_e, E); \
  })

# elif defined __i386__

#  define debugpred__(e, E) \
  ({ long int _e = !!(e); \
     asm volatile (".pushsection predict_data\n" \
                   "..predictcnt%=: .long 0; .long 0\n" \
                   ".section predict_line; .long %c1\n" \
                   ".section predict_file; .long %c2; .popsection\n" \
                   "incl ..predictcnt%=(,%0,4)" \
                   : : "r" (_e == E), "i" (__LINE__), "i" (__FILE__)); \
     __builtin_expect (_e, E); \
  })

# else

#  error "debugpred__ definition missing"

# endif

# define unlikely(expr) debugpred__ ((expr), 0)

# define likely(expr) debugpred__ ((expr), 1)
#endif
```

这些宏大量利用了 GNU 汇编器和链接器在创建 ELF 文件时提供的功能。在 `DEBUGPRED` 情形下，第一条 `asm` 语句定义了三个附加的节（section）；它主要是把关于这些节应当如何创建的信息告诉汇编器。所有节在运行时都可用，并且 `predict_data` 节是可写的。重要的是，所有节名都是合法的 C 标识符。原因很快就会清楚。

`likely` 与 `unlikely` 的新定义引用了与机器相关的 `debugpred__` 宏。这个宏承担以下任务：

1. 在 `predict_data` 节中分配两个字（word），用于存放预测正确与预测错误的计数。这两个字段借助 `%=` 获得唯一的名字；前导的点确保这些符号不会污染符号表。

2. 在 `predict_line` 节中分配一个字，用于存放使用该 `likely` 或 `unlikely` 宏处的行号。

3. 在 `predict_file` 节中分配一个字，用于存放指向使用该 `likely` 或 `unlikely` 宏处的文件名的指针。

4. 根据表达式 `e` 的实际取值，递增为该宏创建的“正确”或“错误”计数器。这里我们不使用原子操作，因为它们要慢得多，而且在发生冲突这种不太可能的情况下，绝对精确并不那么重要。如果想要，改起来也很容易。

`.pushsection` 与 `.popsection` 伪指令在汇编器手册中有描述。有兴趣的读者可以借助手册并通过一些试错来探究这些定义的细节。

这些宏会自动且透明地负责收集关于分支预测正确与错误的信息。现在缺少的是一种取得结果的方法。最简单的做法是为该对象定义一个析构函数，并在其中把结果打印出来。这可以通过如下定义的函数实现：

```c
extern long int __start_predict_data;
extern long int __stop_predict_data;
extern long int __start_predict_line;
extern const char *__start_predict_file;

static void
__attribute__ ((destructor))
predprint (void)
{
  long int *s = &__start_predict_data;
  long int *e = &__stop_predict_data;
  long int *sl = &__start_predict_line;
  const char **sf = &__start_predict_file;

  while (s < e) {
    printf ("%s:%ld: incorrect=%ld, correct=%ld%s\n", *sf, *sl, s[0], s[1],
            s[0] > s[1] ? "   <==== WARNING" : "");
    ++sl;
    ++sf;
    s += 2;
  }
}
```

这里就用上了“节名是合法的 C 标识符”这一事实；GNU 链接器利用它，在需要时自动为节定义两个符号。`__start_XYZ` 符号对应节 `XYZ` 的起始位置，`__stop_XYZ` 则是紧跟在节 `XYZ` 之后的第一个字节的位置。有了这些符号，就可以在运行时遍历节的内容。注意，由于节的内容可能来自链接器在链接时用到的所有文件，编译器和汇编器没有足够的信息来确定节的大小。只有借助这些链接器生成的神奇符号，才能遍历节的内容。

不过，这段代码并不只遍历一个节；这里涉及三个节。既然我们知道，每往 `predict_data` 节加入两个字，就会分别往 `predict_line` 和 `predict_file` 节各加入一个字，我们就不必检查这两个节的边界。我们只需带着指针一路前进即可。

这段代码会为程序中出现的每一处预测打印一行。它会把预测不正确的地方高亮出来。当然，这一点可以改，调试模式也可以限制为只标记那些错误预测多于正确预测的条目。那些才是应当修改的候选对象。还有一些细节会让问题变复杂；例如，如果分支预测发生在某个被多处使用的宏内部，那么所有使用该宏的地方必须一起考虑，才能作出最终判断。

最后还有两点要说明：这种调试操作所需的数据并不少，而且在涉及动态共享对象（DSO）时开销很大（`predict_file` 节必须被重定位）。因此，调试模式不应在生产环境的二进制文件中启用。另外，每个可执行文件和 DSO 都会产生自己的输出，分析数据时必须记住这一点。

[^50]: 至少在使用 GNU 工具链时是如此。

## A.3 测量缓存行共享开销

本节包含用于测量以下两种情形开销的测试程序：变量位于同一缓存行，以及变量位于不同的缓存行。

```c
#include <error.h>
#include <pthread.h>
#include <stdlib.h>

#define N (atomic ? 10000000 : 500000000)

static int atomic;
static unsigned nthreads;
static unsigned disp;
static long **reads;

static pthread_barrier_t b;

static void *
tf (void *arg)
{
  long *p = arg;

  if (atomic)
    for (int n = 0; n < N; ++n)
      __sync_add_and_fetch (p, 1);
  else
    for (int n = 0; n < N; ++n) {
      *p += 1;
      asm volatile ("" : : "m" (*p));
    }

  return NULL;
}

int
main (int argc, char *argv[])
{
  if (argc < 2)
    disp = 0;
  else
    disp = atol (argv[1]);

  if (argc < 3)
    nthreads = 2;
  else
    nthreads = atol (argv[2]) ?: 1;

  if (argc < 4)
    atomic = 1;
  else
    atomic = atol (argv[3]);

  pthread_barrier_init (&b, NULL, nthreads);

  void *p;
  posix_memalign (&p, 64, (nthreads * disp ?: 1) * sizeof (long));
  long *mem = p;

  pthread_t th[nthreads];
  pthread_attr_t a;
  pthread_attr_init (&a);
  cpu_set_t c;
  for (unsigned i = 1; i < nthreads; ++i) {
    CPU_ZERO (&c);
    CPU_SET (i, &c);
    pthread_attr_setaffinity_np (&a, sizeof (c), &c);
    mem[i * disp] = 0;
    pthread_create (&th[i], &a, tf, &mem[i * disp]);
  }

  CPU_ZERO (&c);
  CPU_SET (0, &c);
  pthread_setaffinity_np (pthread_self (), sizeof (c), &c);
  mem[0] = 0;
  tf (&mem[0]);

  if ((disp == 0 && mem[0] != nthreads * N)
      || (disp != 0 && mem[0] != N))
    error (1, 0, "mem[0] wrong: %ld instead of %d",
           mem[0], disp == 0 ? nthreads * N : N);

  for (unsigned i = 1; i < nthreads; ++i) {
    pthread_join (th[i], NULL);
    if (disp != 0 && mem[i * disp] != N)
      error (1, 0, "mem[%u] wrong: %ld instead of %d", i, mem[i * disp], N);
  }

  return 0;
}
```

这里给出这段代码，主要是为了说明如何编写一个用来测量缓存行开销这类效应的程序。有意思的部分是 `tf` 中两个循环的循环体。编译器认识的 `__sync_add_and_fetch` 内建函数会生成一条原子加法指令。在第二个循环中，我们必须“消费”递增的结果（通过那条内联汇编语句）。这条 `asm` 并不引入任何实际的代码；相反，它阻止编译器把递增操作提到循环之外。

第二个有意思的地方是，程序把线程绑定到特定的处理器上。代码假定处理器的编号是 0 到 3，当机器有四个或更多逻辑处理器时通常就是如此。代码本可以使用 libNUMA 中的接口来确定可用处理器的编号，但这个测试程序应当具有广泛的可用性，而不引入这一依赖。用这样或那样的方式把它修好都相当容易。
